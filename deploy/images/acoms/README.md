# ACOMS Docker Image

Containerized ACOMS CLI for operator-driven ACO-MS workflows.

This mirrors the deployment shape used by `4icli`: a small non-root Ubuntu
image, the same Zscaler CA trust setup, a long-running compose service for
`docker exec`, and a workspace mount at `/opt/s3/data/workspace`.

## Vendor zip

The ACOMS CLI zip is a local vendor artifact and is intentionally ignored by
git. Put exactly one zip here before building images:

```bash
deploy/images/acoms/src/<vendor-acoms-cli>.zip
```

During image build the zip is extracted to `/opt/acoms`, the first executable
named like `acoms`, `acoms-cli`, or `acomscli` is linked to
`/usr/local/bin/acoms`, and the container runs as user `care` (`uid=1002`).

## Runtime usage

Build the local image from the ignored vendor zip:

```bash
aco deploy acoms build
```

Start the long-running service:

```bash
aco deploy acoms start
```

Run the CLI:

```bash
docker exec -it acoms acoms --help
```

The working directory is `/opt/s3/data/workspace/bronze`, matching the 4icli
service convention so downloaded/exported files land in the shared workspace.

## Config model

No credentials are baked into the image. Runtime containers consume a persisted
config directory generated by `aco acoms setup`:

```bash
/opt/s3/data/workspace/auth/secrets/acoms/config/
```

On container start, `entrypoint.sh` copies that directory into
`$HOME/.config/acoms-cli/` and verifies Datahub access with `ACOMS_API_ID`.
The container exits instead of staying up if persisted config is missing or
invalid. After successful verification it writes `/home/care/.acoms/auth-ready`,
which backs the compose healthcheck.

For migration, the legacy pre-seeded config directory is still consumed if the
new auth path is absent:

```bash
/opt/s3/data/workspace/bronze/acoms/config/
```

The old runtime behavior of configuring from `ACOMS_API_KEY` /
`ACOMS_API_SECRET` is disabled by default. It can be temporarily re-enabled with
`ACOMS_ALLOW_ENV_CONFIG_ON_START=1`, but the preferred flow is bootstrap first,
runtime read-only after.

## Bootstrap

When ACO-MS issues a new key/secret in the portal:

```bash
aco acoms setup
```

The setup command updates `deploy/.env`, runs `bootstrap.sh` in a throwaway
container, verifies with a real `acoms datahub --view` call, and only then
replaces the persisted config directory. Failed verification leaves the previous
config untouched.

## Diagnostics

Use the shared auth doctor to distinguish IP allowlist, credential, TLS/Zscaler,
and container-state failures:

```bash
aco auth doctor --service acoms
aco auth register-ip acoms --ip <portal-registered-public-ip>
aco auth harden
```

## Files

- `src/*.zip` — local vendor zip, ignored by git
- `Dockerfile` — image definition
- `entrypoint.sh` — optional config seed + command exec
- `bootstrap.sh` — verified config refresh after portal rotation
